## Context & problem

The client runs its business on the PHC ERP. Its contacts, the quotes sent to them and the contracts signed with them all live in the ERP's SQL Server database, but there was no single place to see a contact together with its quotes and contracts, filter that list and take it to Excel.

This was a paid client project, and I owned it end to end. The client isn't named here, and no real data is shown.

## Constraints

- **Read-only.** The tool reads the ERP's data and never writes to it.
- **Large tables.** The ERP's document and document-line tables are large, so nothing could load a whole table into the browser or into memory.
- **Internal only.** The app runs on the client's own server and is only reachable from its local network.
- **Exports people can work with.** The Excel file had to be readable on its own, with the filters that produced it and the headline figures.

## Architecture

<Diagram />

- **App.** A single ASP.NET Core Razor Pages app on .NET 10, with no separate API.
- **Data access.** Dapper runs read-only SQL queries against SQL Server.
- **Dashboard.** Contacts and clients, each with its quotes and contracts, behind a set of filters. Pagination happens on the server, so the browser only receives the page it shows.
- **Export.** The Excel file is written with OpenXML in streaming mode. It opens with a block showing the filters and KPIs, followed by grouped rows that expand to show each contact's documents.
- **Hosting.** The app runs as a Windows Service on Kestrel, on the local network, with a subnet allow-list and rate limiting.

## Decisions & trade-offs

- **Dapper instead of a full ORM.** The app only reads, so hand-written SQL with a light mapper keeps every query explicit. The trade-off: there are no generated queries, and every query is written and maintained by hand.
- **Server-side pagination.** Filtering and paging run in the database, so the page stays light however large the data is. The cost is a round trip to the server for every page.
- **Streaming the Excel export.** Rows are written to the file as they're read, instead of building the whole workbook in memory first, so memory use doesn't grow with the size of the export.
- **A Windows Service on the local network.** Running on Kestrel as a Windows Service fits the client's own server and keeps the tool off the internet. The subnet allow-list and rate limiting add a second layer, so only the client's network can reach it, and only at a reasonable pace.

## Results

The client's team gets one read-only view of contacts, quotes and contracts that already live in the ERP, and an Excel export to share it. No metrics are shown, because the figures belong to the client.
